**Document Status:** Approved for implementation planning

**Date:** 2026-10-05

---

# 1. Purpose

This document defines the AI architecture and behavior for the Inventory Management AI system.

The AI is designed as an intelligent operational assistant that can:

- answer inventory questions
- analyze authorized business data
- identify trends and anomalies
- provide demand insights
- recommend reorder quantities
- recommend suppliers
- generate operational briefings
- summarize reports
- prepare draft actions
- support controlled AI-assisted workflows

The AI must never become an uncontrolled alternative application layer.

The core principle is:

> **AI provides intelligence; application services provide authority.**

---

# 2. Source Authority

This document is governed by:

1. Confirmed Requirement Decisions
2. Business Rules
3. FRD
4. Architecture
5. Database Design
6. API Specification
7. UI Specification

If an AI feature conflicts with a confirmed business rule, the business rule wins.

If an AI feature depends on an unresolved business decision, the unresolved decision remains open.

# 4. AI Non-Goals

The AI is not intended to:

- replace the inventory system
- replace application business logic
- execute arbitrary SQL
- directly access PostgreSQL
- silently modify inventory
- silently change reorder points
- bypass role permissions
- bypass warehouse permissions
- bypass approval workflows
- provide unauthorized cost information
- make accounting decisions
- act as a general unrestricted autonomous agent

# 6. AI Trust Model

The AI operates with several categories of information.

## Trusted system instructions

Highest priority.

Examples:

- safety rules
- tool definitions
- application policy
- authorization constraints

## Application context

Trusted only when generated by the application.

Examples:

- organization ID
- user role
- warehouse scope
- effective permissions

## User request

The user's natural-language intent.

## Retrieved business data

Authoritative data returned through approved application tools.

## User-controlled business content

Potentially untrusted.

Examples:

- product descriptions
- supplier notes
- customer notes
- imported CSV content
- uploaded documents

These must never override system/application instructions.

# 15. Fact vs Recommendation vs Action

The AI must distinguish:

### FACT

Derived directly from authorized data.

Example:

```text
There are 18 units available.
```

### CALCULATION

Derived through deterministic application logic.

Example:

```text
Sales increased 15%.
```

### PREDICTION

Forecast or probabilistic output.

Example:

```text
Demand may increase next week.
```

### RECOMMENDATION

Suggested action.

Example:

```text
Consider ordering 50 units.
```

### ACTION

A proposed or executed business operation.

Example:

```text
I prepared a purchase order draft.
```

# 18. Tool Risk Levels

Tools should have explicit risk classification.

## READ

No mutation.

Examples:

```text
get_inventory_summary
get_stock_movements
```

## ANALYSIS

May perform calculations or analytics but does not mutate business state.

Examples:

```text
analyze_demand
detect_inventory_anomalies
```

## DRAFT

Creates a reviewable draft.

Examples:

```text
create_purchase_order_draft
create_transfer_draft
create_adjustment_draft
```

## HIGH_IMPACT_WRITE

Can cause material business changes and requires explicit human approval.

Examples:

```text
execute_inventory_adjustment
execute_transfer
submit_purchase_order
```

The initial implementation should prefer AI tools that create drafts rather than direct high-impact writes.

# 20. Tool Input Validation

Every tool call must be validated against a strict schema.

Example:

```json

  "product_id": "uuid",
  "warehouse_id": "uuid",
  "quantity": 50
```

```json
{
  "quantity": "a lot"
}
```

The tool should reject malformed parameters before application-service execution.

# 49. AI Action State Rules

## Proposed

AI generated a possible action.

## Draft

Action parameters have been assembled into a reviewable object.

## Pending Approval

Human approval is required.

## Approved

A human approved the proposed action.

## Revalidated

Current data still satisfies business rules.

## Executing

Normal application service is executing.

## Executed

Operation completed successfully.

## Stale

The action is no longer valid because underlying data changed.

## Failed

Execution failed without compromising data integrity.

# 59. Cost Data Protection

If a user lacks cost permission:

The AI must not reveal:

```text

weighted average cost

```

# 60. Tenant Data Protection

AI must never combine data across organizations unless a future platform-level capability explicitly authorizes it.

# 61. Warehouse Data Protection

A warehouse-scoped user cannot use AI to query another warehouse.

Example:

```text

```

The AI should respond without exposing restricted data.


# 101. AI Performance Strategy

Prefer:

```text
small targeted tool calls
+
structured data
+
deterministic analytics
```

rather than sending large raw database dumps to the LLM.

For example:

Bad:

```text
send 100,000 inventory rows to model
```

Better:

```text
database query
 ↓
aggregate
 ↓
top 20 relevant records
 ↓
AI explanation
```

---

# 102. AI Context Efficiency

The application should provide the minimum sufficient context.

Context should include:

```text
user intent
authorization
relevant data
definitions
business constraints
```

Avoid unnecessary historical data.

---

# 103. AI Caching

Cache only where stale data is acceptable.

Do not cache authoritative stock state for action execution.

For recommendations:

```text
cached recommendation
+
data_as_of
```

must be treated as potentially stale.

# 123. Final AI Principle

> **The LLM may decide what information is useful and how to explain it, but it does not decide what the system is allowed to do.**

The application determines:

- who the user is
- what organization they belong to
- what warehouses they can access
- what data they can see
- what actions they can request
- what validations apply
- whether approval is required
- whether the action is still valid
- whether the transaction succeeds

The AI adds intelligence on top of those guarantees.
